# 可信端点与重新发布 1.0.0

## 原因与方案

Halo 容器将用户代理域名解析为 100.64.0.7，HTTPS 和虚拟 Token 的 getMe 请求正常，但插件拒绝非公网地址，并将策略异常降级成 code 0 通用提示。

新增管理员配置 trustedEndpointAddresses，每行或逗号分隔的 `域名=IP` 精确授权，不支持通配符或 CIDR。只允许指定主机访问指定公网、私网或 CGNAT 地址；不允许环回、链路本地、组播和其他保留地址。默认空配置保持原有公网策略。所有 DNS 结果逐个验证并直接交给连接层，不二次解析；HTTPS 443、证书验证、禁止重定向和响应上限保持不变。

策略拒绝使用专用异常类型，输出安全的地址与操作提示，不保留原始异常消息或 Token。

## 实施与验证

1. 先复现现有日志遗漏，补充白名单、主机绑定、混合 DNS、配置与安全日志测试。
2. 实现配置、实际连接地址校验及日志分类，同步设置帮助、README 和项目约定。
3. WSL Docker 完整正式版本构建，独立审查代码。用虚拟 Token 验证实际代理链路，不读取真实凭据。
4. 提交推送并等待 CI，通过后删除旧 GitHub Release 和远端/本地 v1.0.0 标签；对新提交重建标签与 Release，等待 CD 验证、构建与上传成功，下载检查正式 JAR。

用户已明确授权修改与覆盖发布 v1.0.0。现有生产 Halo 的配置与插件安装不在本次发布操作中自动修改。

## 验证结果

- 修改前，地址拒绝日志断言与可信配置 fingerprint 断言分别失败；修改后正式版本 `clean build -Pversion=1.0.0` 通过，包含后端测试、前端 11 项测试、类型检查与打包。
- 独立审查未发现阻塞问题。
- 在 k3s 的 Halo 容器内，使用新 JAR 中的实际 TelegramApi 连接器启动独立临时 Java 进程，使用虚拟 Token `0:diagnostic`。未配置规则时明确提示 `blocked by endpoint address policy: 100.64.0.7`；配置 `telegram.api.mystery0.app=100.64.0.7` 后收到 401，证明 DNS、TLS 与 Bot API 请求已打通。401 是虚拟 Token 的预期结果，不代表真实 Bot 身份验证或消息同步验收。
- 未读取真实 Token、未更换运行中的插件、未重启 Halo，临时探针文件已删除。
